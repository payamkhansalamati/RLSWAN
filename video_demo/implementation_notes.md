# Implementation evidence for the concept film

Inspected 20 October 2026. This is a read-only review of the simulation implementation; no controller or training source was changed. No applicable `AGENTS.md` was found in the project, hidden project directories, or ancestor directories. References below are project-relative file names and line numbers.

## What is implemented

The repository implements **synthetic one-dimensional longitudinal car-following simulation**, not a hospital mobile robot. The README states the scope and explicitly says context is generated by repository code rather than collected from a person or produced by a language model (`README.md:3–7`). The action is one continuous longitudinal acceleration value (`env_car_following.py:550–555`); kinematics update speed and longitudinal separation (`env_car_following.py:846–866`). There is no demonstrated mobile-robot navigation, hardware deployment, camera pipeline, face analysis, speech interaction, or hospital integration in these modules.

### Context source and schema

`ContextModel` combines a hidden synthetic regime, a synthetic physiological signal generator, and a rule-based interpreter (`context_model.py:4–28`, `350–359`, `406–411`). The signals are heart rate, heart-rate variability, respiration, and a synthetic fatigue index. The interpreter derives stress/fatigue proxies, preferred headway, comfort priority, and efficiency priority through explicit formulas, then adds optional Gaussian noise (`context_model.py:263–301`). Calling this an implemented LLM would be inaccurate; the source says its rules mimic the kind of output an LLM might produce (`context_model.py:17–21`).

`ContextOutput.to_array()` contains exactly:

```text
[stress_level, fatigue_level, preferred_headway,
 comfort_priority, efficiency_priority]
```

This is a five-element array (`context_model.py:72–99`). `regime_label` is metadata, not a policy input. **There is no uncertainty/confidence field.** Added signal/context noise is not a calibrated uncertainty estimate (`context_model.py:233`, `287–293`). Any displayed uncertain visual inference or user confirmation in the film belongs to the proposed extension.

### How context enters the policy

The vanilla policy receives five physical values: gap, ego speed, lead speed, acceleration, and jerk. The context policy receives those five plus the complete five-value context array (`env_car_following.py:899–932`). The environment manually scales/clips these observations and training optionally applies `VecNormalize` (`env_car_following.py:911–931`; `train.py:170–178`). The controller registry enables both observation context and context reward for `context_ppo`, and disables both for `vanilla_ppo` (`registry.py:21–25`).

Training constructs a Stable-Baselines3 `PPO` with `MlpPolicy`, using `[256, 128]` policy/value networks for `context_ppo` (`train.py:279–304`). Training environments use a curriculum by default, or mixed synthetic contexts when the curriculum is disabled (`train.py:156–165`). The default curriculum expands from calm to stressed/fatigued and finally switching/both conditions (`config.py:278–289`; `env_car_following.py:934–956`). Training calls `model.learn` (`train.py:330–337`).

At inference, `PPOController.act` normalizes the current observation with stored statistics and calls `model.predict(..., deterministic=True)` (`controllers.py:174–182`). Consequently **a suitably trained policy can change its prediction immediately when its context input changes, without online retraining**. This is an architectural capability, not evidence that every checkpoint learned the intended adaptation or that it transfers to hospital robots. Existing diagnostics can compare predictions across contexts at fixed physical states (`evaluate.py:955–990`, `1023–1043`). No checkpoint or sensitivity result was evaluated for this film; no `.zip` or `.pkl` model artifacts were found in the inspected project tree.

### How reward priorities enter learning

The reward computes a base safety/comfort/efficiency objective plus a scaled context-shaped term (`env_car_following.py:246–259`, `288–340`, `397–408`; `config.py:123–155`). The base includes collision/headway/short-gap penalties, acceleration and jerk costs, a high-jerk cost, speed tracking, and command-change cost (`env_car_following.py:292–326`). Context also modulates the base jerk multiplier using the stress proxy (`env_car_following.py:298–311`).

The context-shaped term uses:

- `stress_level` to scale jerk and preferred-headway shortfall penalties (`env_car_following.py:364–373`).
- `fatigue_level` to scale a smooth-acceleration bonus and an aggressive-positive-acceleration penalty (`env_car_following.py:375–382`).
- Both stress and fatigue for a further bounded caution/short-gap term (`env_car_following.py:384–391`).
- A stability penalty, scenario-dependent gain, clipping, and `context_reward_scale` (`env_car_following.py:346–356`, `393–408`).

The current reward code **does not multiply comfort or efficiency costs by `comfort_priority` or `efficiency_priority`**. Those two values are observed by the context policy; they are not direct runtime reward-weight controls in this implementation. Comments in `config.py:291–292` should not override the executable reward logic. Do not show a fabricated UI in which an LLM directly edits those reward multipliers and instantly changes a fixed policy.

Reward configuration and context-dependent shaping influence learning. Changing reward configuration alone does not update the inference action of an already trained policy. For the film, immediate adaptation must be described as **context-conditioned control**, with **training: context-dependent reward shaping** as the learning mechanism. A more literal “training: context-dependent reward weights” annotation is supportable because stress/fatigue modulate shaping coefficients, but “reward shaping” is more precise.

## Safeguards and their limits

The implementation has acceleration clipping and a bounded speed state (`env_car_following.py:739–740`, `850`; `config.py:55–58`). It has a context-independent emergency-braking shield enabled by default during training (`env_car_following.py:743–747`; `train.py:156–165`; `config.py:289`), but explicitly disabled in the training checkpoint evaluation environment (`train.py:194–202`).

When both context flags are enabled, the environment also applies a context-dependent gap/TTC guard with hysteresis, recovery hold, deadzone, command slew limits, and risk-dependent smoothing (`env_car_following.py:749–839`). These rules can change applied actions at runtime separately from the learned policy. This means the vanilla/context comparison changes more than policy input and reward alone (`README.md:29–33`). Some safeguard thresholds depend on the synthetic context, so do not describe every existing safeguard as context-independent.

An optional hybrid context-PPO/PID controller independently evaluates **physical** gap, closing speed, headway, TTC and required braking (`controllers.py:275–378`). It blends/takes over with PID and applies high-risk/emergency filtering (`controllers.py:568–602`). This is a programmed supervisory mechanism, not an LLM decision. None of these simulation mechanisms is a formal universal safety guarantee, and no safety-validated hospital controller is demonstrated.

For the proposed architecture, depict independent physical safety constraints as a separate guard on motion control, outside LLM discretion. The film's line “Safety limits remain active” describes that proposed separation. It must not be represented as proof of certified or guaranteed real-world safety.
